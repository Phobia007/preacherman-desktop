# Character voice conversation

## Voice configuration draft

### Local Breeze TTS 2

Appearance → Voice is the voice management entry point. Every saved voice returned by the installed Breeze server appears as a tile, alongside imported previews; the 12-preview limit does not truncate the shared Breeze library. Re-entering the page, returning focus from Breeze, or pressing **Refresh Breeze voices** reloads the library. **Create / manage in Breeze** opens its local Chinese interface for voice design, cloning and metadata management.

Clicking a Breeze tile synthesizes a short preview without applying it. Holding Apply saves that voice ID for the current character and selects the local Breeze provider. Conversation replies then use that character's voice through the existing playback, output device and avatar audio path. Selections are independent per character and persist across restart. Missing voices or an offline selected Breeze service produce an error; they never silently substitute another voice. Other providers remain drafts.

The sidecar calls only `http://127.0.0.1:18760`; no API key, frontend secret or configurable remote URL is involved. Refresh can start the existing Windows installation with the fixed `D:\AI\Breeze-TTS-2\Start-Breeze.ps1 -NoBrowser` launcher. Breeze is an independently owned, long-lived service: `D:\AI\Breeze-TTS-2\server-process.json` records its exact PID and `Stop-Breeze.cmd` stops it. Closing Preacherman does not stop another application’s Breeze session. The short launcher child is bounded and tracked by the sidecar. Packaged desktop UI/assets remain self-contained.

Recognition and reply generation continue using the existing Whisper and character execution configuration. Only speech output changes when a Breeze voice is applied. Preview and conversation synthesis are cancellable, have bounded response sizes/timeouts, and repair the completed streaming WAV header before playback.

Asset → Settings → Voice Service stores each character's provider, model, region and optional workspace identifier. Breeze reports its actual local connection status. Other providers are marked **Not connected**: this screen does not save credentials or call their realtime APIs.

Appearance → Voice shows a three-column slanted collection. Import a finished WAV, MP3, OGG or M4A preview (up to 30 seconds and 3 MB), optionally attach its provider voice ID, and click the tile to audition through the selected output device. Auditioning never applies a voice. Hold Apply for 1.6 seconds to persist the character's selection; confirmation appears only after saving succeeds. Breeze selections are active speech connections; imported previews from other providers remain drafts. No default or substitute Master Chief voice is assigned.

Preview files are stored separately under the local service's `voice-previews` directory; `characters.v1.json` contains only metadata and the selected ID. Remove preview deletes an imported preview file and clears its selection. Shared Breeze voices are edited in Breeze rather than deleted from an individual character. Appearance → Accessories uses the same collection frames with an honest empty state until assets are supplied. Both screens retain the existing 3D model and support light/dark appearance.

## Existing conversation runtime

Activate a character in Asset. In that character's Settings → Execution Mode, connect a signed-in Codex CLI or save a tested API connection. The bottom-right waveform starts voice conversation; click it again to stop. The three-dot audio menu retains microphone and speaker selection. No transcript, reply, input field or subtitles are rendered.

Speech recognition uses the installed offline Whisper runtime and cached multilingual base model. An applied Breeze voice supplies cloned speech output; characters without a Breeze selection retain the existing Windows Chinese/English speech synthesis. Recognition language is independent of the English interface. No speech API key is needed; model replies use the selected CLI login or API account. The old Windows dictation route is no longer used for conversation after a real microphone rejection report.

Like a local execution CLI, the speech capability must be installed on the machine: `python.exe` on the desktop process PATH, Python packages `openai-whisper`, `torch`, `numpy`, and `%USERPROFILE%/.cache/whisper/base.pt`. They are already present on the development desktop. The application never downloads dependencies or models on launch, and reports a missing capability audibly instead of silently reverting to the old recognizer. This runtime dependency does not move packaged UI or assets behind a server. Requests run on CPU with four compute threads, one recognition worker at a time, and a 35-second deadline. The worker exits after each request and is killed on cancellation. No GPU memory remains allocated for speech.

Each catalog character has a stable identity, an independent execution selection, rule/skill slots and a memory namespace in `characters.v1.json` under the existing local service data directory. On first access, a character snapshots the global execution default. Later global changes do not replace that selection. API credentials remain in the shared connection store; they are not duplicated in character records. Character identity is supplied as server-owned model instructions. Tool execution remains disabled.

The existing microphone meter feeds a packaged AudioWorklet. It preserves a short lead-in and ends a phrase after one second of silence, with a twenty-second phrase bound and a forty-five-second idle shutdown. The microphone is released while recognizing, waiting for the model and playing a response, then reopened automatically. Stopping, changing character, changing execution settings or unmounting cancels the active request and playback. Audio and transcripts are not written to disk. Recent context is kept only in bounded process memory, isolated by character and voice session, and expires after thirty minutes. Info Map is unchanged.

Whisper receives validated mono 16 kHz PCM audio through JSON stdin. It removes DC offset, brings quiet audio into range with bounded gain, and rejects silence before decoding. Recognition acceptance belongs to that engine rather than reusing Windows confidence thresholds. Two consecutive unrecognized phrases stop listening with an audible microphone troubleshooting prompt instead of repeating forever. Windows synthesis runs a fixed, hidden PowerShell program with JSON stdin and memory streams. User speech never becomes executable code. Requests are bounded, validated and cancelled when the client disconnects; owned children terminate at completion. A deployment must include both the rebuilt sidecar and the packaged host.

Verification: `tests/character-voice.test.mjs`, existing Codex/execution/audio/provider tests, type checking and a real native voice flow in both appearances. Synthetic speech verifies repeatable recognition → real character response → decoded non-silent playback. The native microphone is separately opened and stopped to verify hardware permission and capture. Personal microphone/accent quality still requires the user's own spoken trial.
